## 0. 一句话

上传的照片**先不进入图像库**，先进一个暂存区；用户在列表里给它们起好名字
（可以打一个统一前缀一次改完全部）、处理掉重名，再点「确认导入」正式入库；
点「取消」则一张都不留。

## 1. 用户已拍板的三个决定（2026-09-20）

| # | 问题 | 用户决定 |
|---|---|---|
| 1 | 哪些导入方式要先过列表？ | **只有一次传多张才过**。单张拖拽 / 单选 / 粘贴 → 直接入库（保持现在的快路径） |
| 2 | 手机端能不能改名字？ | **能**。手机上显示同一份列表，能改名、能确认 |
| 3 | 撞名怎么处理？ | **三种都给**：自动加后缀 / 手动改 / 覆盖原图像（覆盖要二次确认） |

### ⚠️ 与需求文档的两处偏离（用户已知情并同意）

| 需求原文 | 本设计 | 影响 |
|---|---|---|
| §3.1.1 / §3.1.2 / §3.1.4：手机单张、拖拽、单张提交、粘贴**都要**进待确认列表 | 单张一律直接入库，**只有 ≥2 张才进列表** | 粘贴一张截图仍然直接入库，名字是「粘贴的图」，得手动改名。**如果这个变扭，改法是一行**（`paste()` 里换成 staged 路径） |

## 2. 用起来是什么样

### 2.1 在测量页一次拖 3 张（会自动跳到图库的待确认列表）

⚠️ 电脑上没有别的多张导入入口：**图库页根本没有上传入口**（没有 file input、
没有 drag 监听）。多张的路径只有「测量页一次拖 ≥2 张」这一条，它传完自动跳到
`/gallery?pending=1` 把这块展开。

图库页 `<main>` 里出现一块待确认区，**展开状态**占满主区域，格子墙让位：

```
待确认导入（3 张 · 11.4 MB）              统一前缀 [EXP0615_    ✕]     [收起]

[缩略图]  IMG_0001.jpg   [前缀][IMG_0001      ]  3.8 MB   ✕移除
[缩略图]  IMG_0002.jpg   [前缀][IMG_0002      ]  4.1 MB   ✕移除
[缩略图]  IMG_0003.jpg   [前缀][IMG_0003      ]  3.5 MB   ✕移除

                                              [确认导入]   [取消]
```

- 前缀框填上之后，每一行输入框前面会**长出一截灰色前缀**，和输入框连成一体、
  看起来像一个框。用户改前缀 → 所有行立刻跟着变，不需要逐行重打。
- 每行的「名称输入框」里**只有后半截**（base）。前缀不落进输入框，
  所以清掉前缀时每一行会自动退回它自己的 base，不需要撤销任何东西。
- 头上的数字 = **正常行**的张数和总大小；有失败行时后面再缀一句
  `· 1 张没成功`，失败行自己不占大小。

### 2.2 收起之后

右上角「收起」把待确认区压成一条横杠，格子墙回来：

```
◤ 待确认导入 3 张 · 11.4 MB            [去命名]  [取消]
```

**为什么要能收起**：这条列表会一直在（刷新也在，见 §7），如果它死占着主区域，
用户想在确认之前先翻翻图库就没法翻了。矛盾时以"图库还能用"优先。

排序下拉框 / 搜索 / 左边的文件夹树在待确认区展开时**都还能用**，只是格子墙被挡着 ——
所以收起之后它们才有意义。

### 2.3 撞名

某行的「前缀+名称」和图像库里已有的一张重名时，那一行：

```
[缩略图]  IMG_0001.jpg   [前缀][IMG_0001      ]  3.8 MB   ✕移除
          ⚠ 图库里已经有一张叫「IMG_0001」的照片，它量过 3 条线
          [自动加后缀]  [手动改]  [覆盖原图像]
```

| 按钮 | 干了什么 |
|---|---|
| 自动加后缀 | 把输入框的内容改成 `IMG_0001 (2)`（就是系统本来会给的名字），警告消失 |
| 手动改 | 把光标放到输入框里，让用户自己打 |
| 覆盖原图像 | 这一行标记成"要覆盖"，变红；**点确认导入时**才真的弹警告 |

「覆盖原图像」的警告原文（数字是实的）：

> 导入后，图库里原来那张「IMG_0001」会被删掉，
> **它上面量过的 3 条线会一起永久消失，找不回来。**
> 原图文件会挪到 `data/trash/`，但测量记录不会。
> 　　　　　　　　　[取消] 　[确认覆盖]

- **默认焦点在「取消」上**（按回车不会误删）。
- 没有任何一行标记成覆盖时，确认导入**不弹**这个框，直接入库。

### 2.4 确认导入

1. 所有正常行入库，用「前缀 + 名字」当名字；空名字的行回退到原始文件名。
2. 跳回图库的格子墙（`/gallery`），新照片排在**最前面**（默认排序就是导入时间倒序）。
3. 列表清空、暂存文件删掉、前缀清空。
4. 若有用原始文件名兜底的行 → 弹提示：
   **「有 2 张图像未命名，已使用原始文件名」**
5. 读不出来的那些红字行 → 一并清掉（它们本来就没入库），提示
   **「3 张没成功的已经跳过」**。

### 2.5 取消导入

二次确认后：列表清空、暂存文件（和它们的小图）删掉、前缀清空、一张都不入库。
文案：**「取消后这 3 张要重新传一遍，确定吗？」**

### 2.6 手机上

同一个列表，紧凑版：一行 = 小图 + 文件名 + 输入框 + ✕；顶部前缀框，
底部两个大按钮「确认导入」「取消」。触屏优先，不做收起（手机上没有格子墙要抢）。

### 2.7 测量页上拖进来

| 拖了几张 | 行为 |
|---|---|
| 1 张 | 老样子：直接入库；当前没打开照片时自动打开它 |
| ≥2 张 | 全部进待确认列表，**页面跳到** `/gallery?pending=1`（图库直接展开待确认区） |

跳走不会丢工作：⭐ 规则保证测量页刷新后自动恢复（照片 / 缩放 / 框选 / 导出设置都在
`localStorage`）。

## 3. 数据模型

两张新表，加在 `app/db.py` 的 `SCHEMA` 里（`CREATE TABLE IF NOT EXISTS` 每次启动都跑，
所以老库**不需要** `MIGRATIONS` 条目 —— 那是给已有表补列用的）。

```sql
-- 待确认导入的暂存条目。没有批次 id：全库共用一份列表。
CREATE TABLE IF NOT EXISTS pending_imports (
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    name              TEXT    NOT NULL,   -- base 名（不含前缀）
    original_filename TEXT    NOT NULL,
    size              INTEGER NOT NULL DEFAULT 0,
    staged_path       TEXT,               -- 相对 STAGING_DIR 的文件名；NULL = 没存下来
    status            TEXT    NOT NULL DEFAULT 'ok',   -- 'ok' | 'failed'
    reason            TEXT    NOT NULL DEFAULT '',     -- failed 时给用户看的中文
    import_source     TEXT    NOT NULL DEFAULT 'unknown',
    created_time      INTEGER NOT NULL
);

-- 单行表，存统一前缀。存服务端是为了手机和电脑看到同一个前缀。
CREATE TABLE IF NOT EXISTS pending_state (
    id     INTEGER PRIMARY KEY CHECK (id = 1),
    prefix TEXT    NOT NULL DEFAULT ''
);
INSERT OR IGNORE INTO pending_state (id, prefix) VALUES (1, '');
```

**为什么没有批次 id**：手机页是「一个 HTTP 请求传一张」，服务端根本看不出
"这 5 张是同一批"。与其让前端编一个批次号传进来（多一个要维护的概念），
不如全局一份列表 —— 用户中途传第二批也只是追加几行。

**为什么 `name` 只存 base**：见 §2.1。前缀在读取时拼接，清掉前缀时各行自动回退。

### 3.1 目录

```
data/
  images/originals/     ← 正式入库的原图（已存在）
  thumbs/               ← 正式图的缩略图（已存在）
  staging/              ← 新增：没确认之前的原图
    thumbs/             ← 新增：暂存图的小图
  trash/                ← 被覆盖 / 被删的原图（已存在）
```

- `config.STAGING_DIR = DATA_DIR / "staging"`，加进 `ensure_dirs()`。
- 暂存小图放 `STAGING_DIR / "thumbs"`。

⚠️ **不能在 config 里写 `STAGING_THUMBS_DIR = THUMBS_DIR / "staging"` 这种派生常量。**
模块级常量在 import 时就求值了，测试里 `monkeypatch.setattr(config, "THUMBS_DIR", tmp_path/...)`
只改了 `THUMBS_DIR`，派生常量还指着用户真实的 `data/` —— 测试会往真库里写东西。
**派生路径一律在调用时算**（`config.STAGING_DIR / "thumbs"`）。

同理，新增 `STAGING_DIR` 之后，**每一个测试 fixture 都必须 monkeypatch 它**
（`tests/` 没有 conftest.py，每个文件自带 fixture，见 `tests/test_api_folders.py:17-25`）。
漏了就往用户真实 `data/` 里写。

## 4. 接口

新文件 `app/api/imports.py`。**同一批处理函数挂两个路由**：

| 路由 | 给谁用 | 前缀 |
|---|---|---|
| `router` | 电脑（本机） | `/api/imports` |
| `phone` | 手机 | `/m/{token}/imports` |

**为什么手机要走 `/m/{token}` 前缀**：`app/main.py:74` 的 `lan_guard` 对非本机请求
**只放行 `/m/<当前令牌>` 开头的路径**，别的全是 403。手机页面上的 JS 直接打
`/api/imports` 会被自己的守卫拦掉。现有手机上传页也是这么做的
（`app/api/mobile.py:142` 打的是 `/m/${token}/upload`）。

令牌本身**不需要在处理函数里再验一遍** —— 中间件已经卡死了：令牌不对的远程请求
在路由之前就 403 了。所以处理函数里**不声明** `token` 参数（声明了会变成
桌面路由上一个必填的 query 参数，桌面全坏）。

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/images/upload?mode=auto\|direct\|pending` | 上传（**改现有接口**） |
| POST | `/m/{token}/upload?mode=...` | 手机上传（同上） |
| GET | `…/imports` | 列表 + 前缀 + 总大小 + 逐行冲突信息 |
| GET | `…/imports/{id}/thumb` | 这一行的小图 |
| PATCH | `…/imports/{id}` | 改这一行的 base 名 |
| DELETE | `…/imports/{id}` | 移除这一行（删暂存文件） |
| PUT | `…/imports/prefix` | 设统一前缀（返回整份列表） |
| POST | `…/imports/confirm` | 确认导入 |
| DELETE | `…/imports` | 取消：清空 + 删文件 |

### 4.1 上传的 mode

| mode | 行为 |
|---|---|
| `direct` | 现在的行为，一字不变：逐张存盘入库，返回 `{"ok": [...], "failed": [...]}` |
| `pending` | 每张都进暂存区（读不出来的也占一行，`status='failed'`） |
| `auto`（默认） | `len(files) >= 2` → 按 `pending` 走；否则按 `direct` 走 |

- 电脑端两个页面都提交**一个请求带多个文件**，所以 `auto` 在服务端数得清。
- 手机端是一个请求一张，服务端数不出总数，**由手机页自己传 mode**：
  `files.length >= 2 ? 'pending' : 'direct'` —— 用户一次选了几张它自己知道。

响应增加一个 `staged` 键（`direct` 模式下恒为空数组）：

```json
{"ok": [...], "failed": [...], "staged": [ {...pending entry...} ]}
```

前端据此判断：`staged.length > 0` → 这批进了列表。

### 4.2 待确认条目的形状

```json
{
  "id": 3,
  "name": "IMG_0001",
  "original_filename": "IMG_0001.jpg",
  "size": 3820000,
  "status": "ok",
  "reason": "",
  "import_source": "upload",
  "conflict": {"image_id": 5, "name": "IMG_0001", "line_count": 3,
               "suggest": "IMG_0001 (2)"}
}
```

- `conflict` 是 `prefix + name`（trim 后）和图像库里某张 **完全同名** 时才有值，
  否则 `null`。
- `line_count` 就是那张已有照片量过几条线 —— 覆盖警告里的数字从这儿来。
- `suggest` = **服务端用既有的 `_unique_name` 算好的**「自动加后缀之后该叫什么」。
  为什么要服务端给：加后缀要避开**库里已经存在的名字**（`IMG_0001 (2)` 被占了就得是 `(3)`），
  这个只有服务端知道。前端自己拼 `name + " (2)"` 会拼出一个同样被占的名字，等于白算。
  前端拿它直接填「自动加后缀」按钮（去掉前缀再填进输入框）。
  实现见 `app/api/images.py` 的 `_conflict()`。
- **名字为空的行、`status='failed'` 的行，`conflict` 恒为 `null`** ——
  前者到确认时才决定名字，后者根本入不了库，都不该弹警告。

### 4.3 GET 列表

```json
{"items": [...], "prefix": "EXP0615_", "total_size": 11400000,
 "ok_count": 2, "failed_count": 1}
```

- `total_size` 只累加真的有暂存文件的那些行（失败行 `size` 不计）。
- 按 `id` 升序（= 上传顺序）。

### 4.4 PATCH 改一行

请求 `{"name": "IMG_0001"}`。返回**这一行**（含刷新过的 `conflict`）。

- **允许空字符串** —— 用户清空重打时中间态就是空的，不该弹 400。
  存成 `''` 表示"到确认时回退到原始文件名"。
- 非空时按现有 `_validate_name` 校验（长度 ≤ 100、非法字符）。
  **不在这里校验前缀拼接后的长度**（前缀会变，校验了也没用），
  留到确认时兜底。

### 4.5 PUT 前缀

请求 `{"prefix": "EXP0615_"}`，返回**一整份列表**（同 §4.3）。

返回整份是因为改前缀会同时改掉**每一行**的冲突状态，逐行刷新反而更绕。

**空字符串是合法的**（= 清掉前缀），列表头上那个 ✕ 就是发这个。
非空时校验：≤ 60 字、不含 `\ / : * ? " < > |`（走 `_validate_name` 的字符规则）。
前缀**不用** `_validate_name` 整个套 —— 它允许为空。

### 4.6 POST 确认导入

请求 `{"overwrite": [7, 9]}`（要覆盖的 pending id；不传 = 一个都不覆盖）。

逐行处理，**每成功一行就删掉那行**，所以中途出错剩下的还留在列表里带红字：

1. `status='failed'` 的行 → 删掉，计入 `skipped`。
2. 暂存文件不在磁盘上了 → 这行标红「暂存的文件找不到了，移除这一行重新传」，跳过。
3. 算最终名：`base = name.strip() or _name_from_file(original_filename)`；
   `final = prefix + base`。空 base 计入 `unnamed`。
4. 这一行被标记了覆盖、且库里真有同名的 → `storage.trash_file()` +
   `db.delete_image()`（级联删掉标定和测量），然后**用原名**插入。
5. 否则 → `_unique_name()` 拿到不撞的名字再插入。
6. `storage.store_original(暂存文件字节)` 挪进正式库（重读一遍而不是 move ——
   和直接导入走**完全同一条**校验+命名路径，零新增失败模式）。
   代价：50 张 4MB 的图约 200MB 的读+写，1 秒量级，可以接受。
7. 删掉暂存文件 + 它的暂存小图 + 这一行的数据库记录。

返回：

```json
{"imported": 3, "skipped": 1, "unnamed": 2, "overwritten": ["IMG_0001"]}
```

**最后一步清空前缀**（`pending_state.prefix = ''`）。

⚠️ 名字总长兜底：`_validate_name(final)` 失败（前缀+名字超 100 字）→ 这一行
标红「名字太长，改短一点再确认」，跳过。界面上输入框有 `maxlength = 100 - 前缀长度`
挡着，正常走不到这里，服务端仍然要挡。

### 4.7 DELETE 取消

删掉所有暂存文件 + 暂存小图 + 全部 `pending_imports` 行 + 清空前缀。
返回 `{"cleared": 3}`。

### 5.1 `_store` 抽取（`storage.py`）

```python
def _store(data: bytes, dest: Path) -> str:
    """先验后写，返回**相对 dest 的文件名**。坏图片抛 ValueError。"""
    ext, _w, _h = sniff(data)
    dest.mkdir(parents=True, exist_ok=True)
    name = f"{int(time.time() * 1000)}_{hashlib.sha1(data).hexdigest()[:12]}{ext}"
    (dest / name).write_bytes(data)
    return name


def store_original(data: bytes) -> str:
    config.ensure_dirs()
    return _store(data, config.IMAGES_DIR)


def store_staged(data: bytes) -> str:
    config.ensure_dirs()
    return _store(data, config.STAGING_DIR)
```

`resolve_staged(stored) -> Path` = `config.STAGING_DIR / stored`。

`discard_staged(stored, pid) -> bool`：**真删**（不是挪进 trash），
并且删掉 `STAGING_DIR/thumbs/{pid}.jpg`。守卫按 `trash_file` 的老规矩来 ——
`resolve()` 之后判断是否在 `STAGING_DIR` 底下：

```python
def _under(p: Path, root: Path) -> bool:
    try:
        return p.resolve().is_relative_to(root.resolve())
    except OSError:
        return False


def _under_data(p: Path) -> bool:          # 老函数，语义一字不变
    return _under(p, config.DATA_DIR)
```

理由和 `trash_file` 的 docstring 一样：`Path("data") / "D:/.../样品集/图.jpg"`
会返回右边那个绝对路径。**先判断再删**，否则删的是用户的原始素材。

## 6. 前端

### 6.1 图库页

`<main>` 里、`#grid` 之前插一块 `#pending`（默认 `hidden`）。`load()` 先拉
`/api/imports`：非空就渲染它（展开或收起），空就整个藏起来。

- 复用页面上已有的 `send()`（统一 fetch + 错误处理）、`toast()`、`ask()` 对话框。
- 展开时给 `<main>` 加一个 class，用 CSS 把 `#grid` / `#empty` / `#pager` 隐藏
  （不是删掉，收起后原样回来 —— 不能重建 DOM，否则滚动位置和选中状态会丢）。
- 输入框改成"前缀灰条 + 输入框"两个元素贴在一起。**前缀变化时只改灰条的文字**，
  不碰输入框的 value —— 碰了的话用户正在打字的行光标会跳。
- 输入框 `input` 事件 **debounce 300ms** 后 PATCH，拿回来的 `conflict` 只更新
  那一行的警告条。**不要整块重渲染**，那会把焦点抢走。
- 展开 / 收起的状态存 `localStorage` —— ⭐ 规则要求刷新后保持现状。
  用户收起之后刷新，不该又弹开把格子墙挡住。
- `?pending=1` → **强制展开**（从测量页跳过来时用），并把这个状态写回 `localStorage`。

### 6.2 测量页

`uploadFiles()` 里，上传完拿到响应后：

```js
if (d.staged && d.staged.length) {
  location.href = '/gallery?pending=1';
  return;                       // 别再走"自动打开第一张"那段
}
```

其余逻辑（`direct` 模式下的行为）一行不改。

### 6.3 手机页

`_PAGE` 里加一段列表 UI，调 `/m/${token}/imports`。触屏优先：
按钮高 ≥ 44px、输入框 `font-size:16px`（小于 16px 时 iOS 会放大页面）、
不做收起。上传循环结束后刷新列表。

## 7. 刷新就还在（⭐ 规则）

待确认列表**整个存在服务端**（`pending_imports` 表 + `data/staging/` 里的真文件），
所以刷新页面、关掉浏览器、甚至重启工具，它都还在。这是必须的：

- 手机和电脑要看同一份列表 —— 浏览器内存里存不了。
- 用户把「刷新」当"卡住了的恢复手段"，刷新丢列表等于丢工作。

**不做的**：暂存文件**不自动清理**。用户传完不做任何操作就关掉电脑，文件一直留着。
理由是怕"传完出去开个会回来东西没了"。代价是 `data/staging/` 会慢慢占地方 ——
所以列表头上**必须显示总大小**（`11.4 MB`），用户看得见就能自己决定清不清。
和 `data/trash/` 目前"只进不出"的取舍一致。

## 9. 已知风险

1. **覆盖是唯一会永久毁数据的操作**：原图进 `data/trash/` 还能捞，但那张照片上的
   标定和测量记录**不可恢复**。所以：默认加后缀、覆盖要显式点按钮、警告里写清
   具体几条线、焦点默认在「取消」。
2. **暂存目录只进不出**（§7）。列表头上的总大小是唯一的提示。
3. **前缀会套在所有行上**，包括那些本来不想要前缀的行。要单独一张不带前缀，
   只能确认之后再改名。这是"前缀存服务端 + 逐行只有 base"这个模型的直接代价。
4. **手机页的列表 UI 是第二份实现**（图库页一份、手机页一份）。故意的：
   手机要触屏尺寸、图库要密集排布，共用一套 CSS 只会两边都别扭。
   代价是以后改文案要改两处。
5. **确认导入不是原子的**：50 张跑到第 30 张出错，前 29 张已经入库了。
   剩余行留在列表里带红字，用户能接着确认。这比"全有或全无"更好用，
   但用户要明白"确认"可能只成功一部分。
6. **`API_VERSION` 5 → 6**：用户双击 `启动.bat` 时如果端口上还跑着旧进程，
   `launch.py` 靠这个数字认出版本不一致并换端口，不会出现"新页面打旧接口"。
