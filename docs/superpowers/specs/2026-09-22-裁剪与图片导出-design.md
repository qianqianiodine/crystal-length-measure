## 一、C —— 裁剪

### 1.1 用起来是这样

侧栏「导出」面板里，那个「框选导出区域」开关改叫「**裁剪**」。行为：

| 用户做什么 | 看到什么 |
|---|---|
| 勾上「裁剪」 | 画面回到**整张图** + 一个白框（可拖四边、拖白点改大小）。没有框就提示「在图上按住左键拖出要保留的范围」 |
| 拖框 / 调框 | 画面**一直是整张图**（要看得见自己在切掉什么），框上实时显示「800 × 600 像素」 |
| 点「**裁好了**」 | 勾选自动取消，画面切成裁完的那块，框藏起来 |
| 点「**回到原图**」 | 裁剪取消：画面回整张图，框一起没了，要重裁就重新拖。**已在整张图时按钮是灰的** |

裁剪一旦生效，**这张图在哪儿都是裁过的**：测量页画布、图库卡片、导出的 PNG、导出文件夹里的图。

### 1.2 裁剪只改"怎么看"，一个字节的数据都不动

- 圆、测量线的坐标**仍然按原图存**。裁完之后继续拖圆、拉线，数值照样准。
- `um_per_px` 是按每张图单独存的，不受裁剪影响。
- 原图文件不动，也**不做**「裁完重新存一份」那种事。

这是能这么做的关键：画布只是**换了个视口**，坐标系没变。

### 1.3 数据

**新列 `images.crop`（TEXT，JSON）**，`NULL` = 不裁剪。

```json
{"x0": 120.0, "y0": 340.0, "x1": 920.0, "y1": 940.0}
```

坐标是**原图像素**，左上原点，和 `S.crop` 完全一致。

加列走现成的 `MIGRATIONS` 列表（`app/db.py:142`），和 `enhance` 一模一样，
**不需要重建表**。老库自动补列，老记录是 NULL = 不裁剪，行为不变。

⚠️ **不用 `images.transform`**。那个字段装的是透视校正矩阵 `{"H": ...}`，
和裁剪是两回事；而且 `exporter.py:127` 会去它里面找 `enh`（见 §3）。
新开一列更清楚，也和 `enhance` 的既有做法一致。

### 1.4 接口

```python
class CropIn(BaseModel):
    # None = 取消裁剪。这是 PUT，整个资源替换，所以不裁剪就是 null。
    x0: float | None = None
    y0: float | None = None
    x1: float | None = None
    y1: float | None = None


@app.put("/api/image/{image_id}/crop")     # 和 /enhance 做邻居，同样是 PUT
def put_crop(image_id: int, body: CropIn, conn=Depends(get_db)) -> dict:
    """记下这张图裁到哪。只决定**画出来什么样**（页面、图库缩略图、导出图都算），
    原图一个字节都不动、坐标也不受影响 —— 所以一条测量记录都不用重算。"""
```

- 四个数**要么全给、要么全不给**。只给一半 → 400「裁剪参数不对」。
- 不是有限数 → 400。
- `x1 - x0` 或 `y1 - y0` 小于 **8 像素** → 400「裁得太小了，再拖大一点」。
- **不做**边界钳制（服务端此刻没载图，不知道宽高）。越界在**渲染时**钳制 ——
  那时候图就在手上，顺手就夹住了。

解析和切片只有一份实现，放在 **`app/exporter.py`** —— 它本来就拥有 `crop=` 这个公开概念
（`build_annotated_image` 的签名里就有）：

```python
def parse_crop(raw: str | None) -> dict | None
    """images.crop 那一列（JSON 字符串）→ {"mode":"rect","rect":[x0,y0,x1,y1]}。
    空 / 坏数据 / 形状不对，一律 None（= 不裁剪）。"""

def apply_crop(img: np.ndarray, crop: dict | None) -> np.ndarray
    """按裁剪框切片，**越界自动夹到图内**。crop 为 None 就原样返回。"""
```

`thumbs.py` 也要用这两个（见 §2.2），**函数内 import** 即可 ——
在跑起来的应用里 `exporter` 本来就已经加载了，不会真多出开销。

`GET /api/image/{id}`（`main.py` 的 `_state`）和 `_summary()`（图库卡片）都要多返回一个 `"crop"`，
前端才拿得到。`_summary` 还要多返回 `"tags"`（D 要用）。

### 1.5 画布渲染

- `render()` 画图时从 `drawImage(img, 0, 0, ...)` 改成
  **`drawImage(img, cx0, cy0, cw, ch, ...)`** —— canvas 自带的源矩形裁剪，一行的事。
- **`cropMode` 为真时永远画整张图**（否则没法调框）。
- `fitView()`（双击复位也算）适应的是**当前显示的那块**：裁剪模式 = 整张；否则 = 裁剪框。
- 坐标映射 `toImg() / toS()` 只多减一个裁剪原点，圆和线的数据一个字节都不改。
- `scaleBarInfo()`（`measure.html:753`）里挑标尺长度用的 `regionPx`：
  现在写的是 `cropChoice === 'manual' && S.crop ? …`，改成 `S.crop ? (S.crop.x1 - S.crop.x0) : S.W`。
  （这条必须跟着改，否则标尺长度是按整张图挑的，裁完导出图里的标尺会短一截。）

### 1.6 「聚焦到第几条测量线」保留

原来的「裁剪」下拉框（`#exCrop`）里除了「手动框选」还有「聚焦到第 N 条」。
**保留**，改成裁剪面板里的一个快捷方式：选一条测量线 → 框自动套到它周围 → 还能接着手调。

- 理由：删掉要连带删后端 `_parse_crop` 的 `focus:` 分支和
  `tests/test_api.py::test_export_png_focus_crop_is_smaller`，改比留费事；
  而且本项目踩过「搬界面按元素清单搬，丢掉了能力」的坑（见 `learnings.md`）。
- 下拉项的构成：
  - `不裁剪（整张）` —— 选它 = 点「回到原图」
  - `手动框选（800 × 600 像素）` —— **只在 `S.crop` 存在时出现**，且是 `disabled` 的
    （它是当前状态，不是一个动作）
  - `聚焦到第 1 条（345 μm）` …… 每条测量线一项
- **这个下拉框不存任何状态** —— 显示什么是完全由 `S.crop` 推出来的，选中项不是一个"模式"。
  所以旧代码里 `cropChoice` 这个字段**整个删掉**（见 §1.7）：点「聚焦到第 N 条」
  = 算出一个框 → 存进 `S.crop` → 进入裁剪模式，之后照样能手调；
  再换回手动框也不会出现"界面说聚焦、实际是手动"那种对不上的状态。
- 用户明说「我自己会保证页面完整」，所以这个快捷方式他大概率不用 —— 留着不碍事。

### 1.7 刷新保持现状

⭐ 铁律不变，只是**裁剪的来源换了地方**：

| 状态 | 现在 | 改成 |
|---|---|---|
| 打开的是哪张照片 | localStorage | 不动 |
| 缩放 + 平移 | localStorage | 不动 |
| **裁剪框（裁到哪）** | localStorage | **进数据库**（服务器上），刷新后从 `GET /api/image/{id}` 拿回来 |
| **裁剪模式开关（正在不在调框）** | localStorage | 不动 —— 这是界面上的临时状态，不是事实 |
| 导出面板勾选框 / 下拉框 | localStorage | 不动 |

`saveSession()` 里**去掉** `crop` 和 `cropChoice`（服务端管了），**保留** `cropMode`。
老 localStorage 里残留的 `crop` 字段直接忽略（`readSession` 不再读它），不用写迁移。

## 二、C 的必然后果：缩略图缓存

### 2.1 问题

`app/thumbs.py` 的文档字符串写死了这个前提：

> `images.id` 是 AUTOINCREMENT、**永不重用**，所以缓存不会串图；
> 原图一旦导入也不会再被改写，**因此不需要任何失效逻辑**。

`app/api/images.py` 的 `thumb()` 据此回了 `Cache-Control: max-age=86400`，
注释里写着「这张缩略图的内容永远不变，放心让浏览器长缓存」。

**C 把这个前提打破了。** 不处理的话：用户裁完图去图库，卡片上还是旧图，
**要等 24 小时或者手动清缓存**才更新 —— 用户会以为裁剪没生效。

### 2.2 两处一起改

**① 缩略图要画裁剪 + 亮度和对比度**

`thumbs.ensure()`（`app/thumbs.py:34`）现在只做「读原图 → 缩放」，
`ensure_at(src, dst)`（`:39`）是它的实体。改成「读原图 → 应用增强 → 裁到裁剪框 → 缩放」：

```python
def ensure(src: Path, image_id: int, *,
           crop_raw: str | None = None, enhance_raw: str | None = None) -> Path | None:
    return ensure_at(src, path_for(image_id), crop_raw=crop_raw, enhance_raw=enhance_raw)
```

调用方（`thumb()`，`app/api/images.py:272`）把库里那两列**原样**递进来：

```python
p = thumbs.ensure(storage.resolve_path(row["path"]), image_id,
                  crop_raw=row["crop"], enhance_raw=row["enhance"])
```

- 为什么不只画裁剪：`enhance` 是同一类东西（都只决定"这张图看起来什么样"），
  只画一半的话，用户调完亮度，图库卡片还是旧的 —— 同一个 bug 换个字段再来一次。
- 顺手的好处：图库卡片从此是这张图**真实的**预览。
- **不做透视校正**（`transform.H`）。图库卡片今天是原图，改成校正后的版本是另一件事，
  不在这一轮。要用的两个处理都在 `exporter.parse_crop / apply_crop`（§1.4）和
  `enhance.parse_enhance / apply_enhance` 里，函数内 import。

⚠️ **`api/imports.py:92` 那条路（待确认导入列表）不用改** —— 暂存区的照片还没进
`images` 表，既没裁剪也没调过画质，两个参数不传就是原行为，**零 diff**。

**② 裁完 / 调完亮度要删掉旧缩略图**

`thumbs.drop(image_id)` —— 已经有了，叫 `drop_staged` 的兄弟，3 行。
在 `put_crop` 和 `put_enhance` 里各调一次。

**③ HTTP 缓存从「24 小时」改成「每次问一下」**

```python
return FileResponse(p, media_type="image/jpeg",
                    headers={"Cache-Control": "no-cache",
                             "X-Content-Type-Options": "nosniff"})
```

`no-cache` **不是"不缓存"**，是"可以存，但每次要问一下服务器变没变"。
Starlette 的 `FileResponse` 自带 `ETag` + `Last-Modified`，
文件没变就回 **304 空响应**（几十字节），变了才重传。

- **代价**：图库一屏 48 张卡片，翻页时多 48 个很小的请求。
  本地工具，可以忽略。这是为正确性付的钱。
- **备选方案**（不采用）：URL 上挂个版本号 `?v=<裁剪哈希>`，可以继续长缓存。
  但它要求 `_summary` 多返回一个版本字段、前端多拼一个参数、且**每次改动都得记得更新它** ——
  多一个能忘记的地方，不值。

## 三、顺手要修的既有 bug（D 会把它暴露出来）

`app/exporter.py:125`：

```python
    if img_row["transform"]:
        try:
            t = json.loads(img_row["transform"])
            H = t.get("H")
            enh = t.get("enh")        # ← 全项目没有任何代码往这里写
```

而界面把亮度/对比度/饱和度存在 **`images.enhance` 列**里
（`main.py:388`，读取在 `main.py:174` 的 `_load_enhance`）。

**后果**：服务端生成的标注图**永远不带用户的画质调整**。

**现在为什么没人发现**：界面上「导出图片」是浏览器自己画的（`renderExport`，`measure.html:1615`），
服务端那条 `/api/image/{id}/export.png` 只有测试在调。所以这个 bug 是潜伏的。

**为什么 D 会踩到**：批量导出必须服务端生成（一次三十张，不可能让浏览器画），
走的正是这条路。不修的话，**导出文件夹里的图会比屏幕上暗一档**，
而用户会以为导出坏了。

**修法**（删 3 行、改 1 行）：

```python
    H = None
    if img_row["transform"]:
        try:
            H = json.loads(img_row["transform"]).get("H")     # 只留 H
        except (ValueError, TypeError):
            pass
    ...
    enh = enhance.parse_enhance(img_row["enhance"])           # ← 改从这里读
    if enh != enhance.NEUTRAL:
        base = enhance.apply_enhance(base, enhance.EnhanceParams(**enh))
```

**解析那一列的逻辑已经有一份现成的**：`main.py:174` 的 `_load_enhance(row)`
（「没调过、或者存档坏了，一律回中性值」）。**原样搬进 `app/enhance.py`**，
连同 `ENHANCE_RANGE` / `ENHANCE_NEUTRAL` 两个常量（`main.py:170-171`），
`main.py` 里留 import —— **行为零变化**，但 `exporter` 和 `thumbs` 都能用同一份了。

> 为什么不直接 `from app.main import _load_enhance`：`main.py` 自己 import 了
> `exporter`（`export_png` 要用），反过来 import 就是环。

名字**不改**，仍叫 `ENHANCE_NEUTRAL`，`main.py` 直接 import 它（引用处照旧）——
不搞别名，一个新名字就是一处将来会分叉的地方。

## 四、D —— 图库批量导出图片

### 4.1 用起来是这样

图库里勾选若干张照片 → 底部操作栏多一个「**导出图片**」→ 点它 → 等一会儿 →
**硬盘上生成一个文件夹，并自动弹出来**。

用户 2026-09-22 拍板（见 §零 第 12~14 条）：生成真文件夹不用解压、图片要带标尺和测量线、
没归类的放「未分类」。

```
D:\vs_claude_test\晶体大小测量\
  导出\
    2026-09-22_143052\          ← 生成完自动弹出这个窗口
      样品1\
        样品1_A1-1.png
        样品1_A1-2.png
      样品2\
        样品2_B3-1.png
      未分类\
        IMG_2203.png
        IMG_2204.png
```

- 导出目录固定在**工具根目录下的 `导出\`**（和 `data\`、`web\` 并排）。
  自动弹出来的就是它，下次也知道去哪找。`导出\` 加进 `.gitignore`。
- **每次导出建一个新文件夹**（`日期_时分秒`），**绝不覆盖上一次的** ——
  导出是不可逆的磁盘写入，宁可多占点地方，也不做"悄悄盖掉"这种事。
- 生成完弹一句：「导出了 30 张，在 `导出\2026-09-22_143052`，已经帮你打开了」。

### 4.2 标签怎么填

**图库卡片底部多一个按钮**，和「归档…」并排：

- 没标签时写「**标签…**」；有标签时直接显示 `A1-1`，点它改。
- 视觉上和「归档…」一个套路（本项目已有的一致性），一眼能扫出哪些还没标。

**批量**：选中多张 → 操作栏「**打标签**」→ 弹出一张表：

```
┌ 打标签 ─────────────────────────────────────┐
│  [小图] IMG_2201.jpg    [A▾] [1▾] [第1个孔▾] │
│  [小图] IMG_2202.jpg    [A▾] [1▾] [第2个孔▾] │
│  [小图] IMG_2203.jpg    [B▾] [3▾] [第1个孔▾] │
│  …（可滚动）                                  │
│                        [取消]     [确定]     │
└──────────────────────────────────────────────┘
```

- **每行左边一定有缩略图 + 名字** —— 用户说了「我不一定是按照顺序拍的」，
  没有缩略图就是闭着眼睛填。
- 三个下拉：字母 `A~H`（8 项）、数字 `1~12`（12 项）、`第1个孔/第2个孔`。
  每个都带一个空的「—」选项（= 这张不标）。
- **不自动编号、不猜顺序。** 用户对着缩略图一张张选。
- 三个下拉**都选了**才算一个完整标签，拼成 `A1-1`；
  只选了一部分（比如选了 A 没选数字）→ 这一行按"不标"处理，提交前提示。
- **提交前查重**：两行拼出同一个标签就标红，不让提交
  （`A1-1` 重复就等于这张图是哪份样品说不清了，而 30 行 × 3 个下拉手填很容易点错）。
- 单张那个入口复用**同一个组件**，只是一行。

**存储**：写进已有的 `images.tags`（TEXT，JSON 数组，默认 `'[]'`）——
一个标签就是 `["A1-1"]`。不新开列：`tags` 已经在 `UPDATABLE_FIELDS` 白名单里
（`db.py:116`），`PATCH /api/images/{id}` 的注释也早写着「标签/收藏等画廊做出来再加」。
界面这一轮只用到一个标签，但数组结构留着，以后要多标签不用改库。

### 4.3 目录和文件名怎么定

**目录**：照搬网页里那棵文件夹树。`folders` 表是 `parent_id` 自引用的，
**能套层、层数不限**（`db.py:61`），所以导出时也套层，不拍平。
重建某一层的路径靠沿 `parent_id` 往上走（文件夹总共几十个，不追求效率）。

**文件名**：

| 情况 | 文件名 |
|---|---|
| 在文件夹 `样品1` 里，标签 `A1-1` | `样品1_A1-1.png` |
| 在文件夹 `样品1` 里，没标签 | `IMG_2201.png`（原文件名） |
| 未分类，有标签 `A1-1` | `A1-1.png` |
| 未分类，没标签 | `IMG_2203.png`（原文件名） |

- 前缀用的是**直接父文件夹**的名字，不是整条路径 —— 套层时
  `样品A\6月批次\` 里的图叫 `6月批次_A1-1.png`。
- 用户原话：「图片的命名改成文件夹标签 + 三个下拉表格的标签」。
  目录已经说明了归属，文件名里再带一次是**故意**的冗余 ——
  图片被拖出文件夹（进 PPT、发微信）之后，自己还认得出来是哪份样品。
- 原文件名可能是 `.jpg`，统一落成 `.png`（输出的就是 PNG）。

**一张图同时在好几个文件夹里**（`image_folders` 是多对多，`db.py:71`）：
**每个文件夹里都放一份**，各自按所在文件夹取前缀（`样品1\样品1_A1-1.png`
和 `样品2\样品2_A1-1.png` 是同一张图的两份）。和 `copy_folder` 的既有定案一致
（`db.py:500`「副本里的照片是『也放进来』，不是『再存一份』」）——
导出只是把"多个归属"如实摊开，不替用户挑一个。

⚠️ **为什么不做「正在生成第 12/30 张」的进度条**（我先前口头说过要做，这里改主意并说明理由）：
真进度要么让服务端开后台线程 + 任务表轮询，要么用流式响应 —— 两者都会让
「POST 一下拿到结果」变成一个**有竞态、难测**的东西。而**同步**的版本
一个测试就能钉死（POST → 断言文件夹里躺着 3 个能解开的 PNG）。
改成：前端一个转圈的提示 + 走秒 + 一句「**照片多的时候要等十几秒，别刷新**」。
用户真正的风险是**中途刷新、结果看不到**，这句话直接治它。

- 服务端为每张图生成一张 PNG（见 4.4），按 4.3 的规则放进文件夹。
- **不存在的 id 跳过并记进 `failed`**，不报错（别人刚删掉），其余的照常导出。
- 列表空、或者勾的 id 一个都找不到 → 400「没有可导出的照片」。
- **全程只读**：不改数据库、不改照片文件（和 `exporter.py` 一样的铁律）。

### 4.4 图片怎么生成

一个 `export_image(conn, image_id)`，就这一个函数。标定过的画标尺和测量线，
没标定的退回干净原图。**放 `app/exporter.py` 里**（它已经在管"渲染一张导出图"这件事），
不新开文件 —— 这个函数总共十几行，`build_annotated_image` 就在隔壁。

```python
def export_image(conn, image_id: int) -> np.ndarray:
    """导出用的一张图。标定过的画标尺和测量线，没标定的就是干净原图。"""
    row = db.get_image(conn, image_id)
    crop = parse_crop(row["crop"])                   # 空/坏 → None
    try:
        # 标定过的：标尺、测量线、编号它都画；crop= 由它自己的视口逻辑处理
        return build_annotated_image(conn, image_id, crop=crop,
                                     supersample=1, show_notes=False)
    except ValueError:
        # exporter.py:121「该图像尚未标定，请先完成标定再导出」——
        # 画不出标尺，退回"屏幕上看到的样子"（§零 第 6 条决定）
        img = imageio.load_rgb(_source_path(row["path"]))
        enh = enhance.parse_enhance(row["enhance"])
        if enh != enhance.ENHANCE_NEUTRAL:
            img = enhance.apply_enhance(img, enhance.EnhanceParams(**enh))
        return apply_crop(img, crop)
```

- `supersample=1` = **原始分辨率，不缩小**。这是给论文 / PPT 用的，不是缩略图。
  （换算一下：手机照片 12 MP 存成 PNG 大约 10~20 MB，勾 30 张就是几百 MB。
  这是用户明确要的 —— 要能直接拖进 PPT。真嫌大再说，不做"导出前选尺寸"。）

**这里几乎没写新渲染代码**，因为服务端那套本来就支持：

- `build_annotated_image(crop={"mode":"rect","rect":[x0,y0,x1,y1]})` **已经存在**，
  而且文档字符串明确写着「crop 的坐标以原图坐标系表达，内部已负责把端点与裁剪框
  统一映射到绘制坐标系」。标尺、测量线、编号它都画。
- 有 6 个测试在跑这条路（`tests/test_api.py::test_export_png_*`）。
- 所以 D 复用 `crop={"mode":"rect", ...}`，**不为裁剪新写任何绘制代码**。

编码用 `cv2.imencode(".png", img[:, :, ::-1])`（RGB→BGR），
和 `main.py:447` 一致 —— **不走 `cv2.imwrite`**（中文路径会静默失败，项目铁律）。

### 4.6 路径安全与重名

⚠️ **文件夹名和照片名都是用户输入的字，会被当成磁盘路径用。** 这是这一轮唯一一处
"用户的字变成文件系统操作"的地方，必须夹住。不夹住的后果：

- 文件夹叫 `..\..\Windows` → 文件写到工具目录外面去
- 文件夹叫 `D:\某处` → **绝对路径**，`pathlib` 会整个丢弃左边
  （项目实测过这个行为，见 `learnings.md` 里 `data/` + `D:/...` 那条）
- 文件夹叫 `CON` / `NUL` / `PRN` / `AUX` / `COM1` → Windows 保留设备名，建不出来
- 名字里有 `< > : " | ? *` 或结尾带空格 → Windows 直接拒绝

所以有一个 `_safe_segment(name) -> str`，**每一层文件夹名和文件名都过一遍**：

1. 去掉 `..`、`/`、`\`、盘符（`^[A-Za-z]:`）
2. 非法字符 `< > : " / \ | ? *` 和控制字符 → `_`
3. 去掉**结尾的空格和点**（Windows 会静默截掉，导致"文件明明建了却找不到"）
4. 撞上保留设备名（大小写不敏感，`COM1`~`COM9`、`LPT1`~`LPT9`）→ 前面加 `_`
5. 截到 60 字符；空了 → `未命名`
6. **最后再断言一次**：拼出来的绝对路径必须仍在 `导出/` 底下（`os.path.commonpath`）。
   前 5 条是"尽量修好"，这条是"修不好就别写"。

⚠️ **重名**：同一批里两张图算出来同一个文件名（跨批次重复填 `A1-1` 是允许的，
见 §六 第 8 条）→ 后一个自动变 `A1-1 (2).png`，并在结果里数出来：
「有 2 张重名，已自动加 (2)」。**绝不静默覆盖** —— 那会丢掉一张已经量好的图，
而用户不会知道。

> 依赖：**不需要任何新东西**。原来 Excel 要的 `openpyxl` 现在完全用不上了，
> `requirements.txt` 不动，同事那个免安装包不用重打（用户选的「先只管本机」也就
> 不再是问题了 —— 他只是暂时用不到这个功能，没有任何"点了会崩"的路径）。

## 六、已知风险（动手前讲清楚后果）

1. **裁剪会把标定圆切到画面外**。长度照样算得对（比例尺按每张图单独存），
   但那个圆看不见了，也就没法再拖它重新标定。
   → 裁剪面板上常驻一句提示：「裁剪后看不到标定圆了，要重新标定得先点『回到原图』」。
   （**只在圆真的会被裁出去时才显示** —— 一个包含判断，避免天天喊狼来了。）
2. **缩略图的 HTTP 缓存从长缓存改成每次重验证**。网络请求变多（每次都很小）。
   换来的是裁完刷新立刻正确。这是**故意**的取舍。
3. **裁完删缩略图是同步的**。`thumbs.drop()` 在 `put_crop` 里跑，
   下一次请求图库会重新生成 —— 第一次翻到那页会稍慢一点点（一张几十毫秒）。
4. **导出的文件夹会越攒越多，而且刻意不做自动清理**。
   每次导出建一个新文件夹（不覆盖，见 4.1），跑上半年 `导出\` 底下会躺着几十个
   `2026-09-22_143052` 这样的目录。**这是故意的** —— 自动删用户的照片是不可接受的风险。
   单次导出可能几百 MB（见 4.4），磁盘满了要用户自己清。
5. **一张图量了多个晶体时，裁剪只能框住一个**。
   用户说会自己保证取景完整，所以按他的判断走。
6. **文件夹名和文件名会被「洗干净」**（见 4.6），所以导出的名字
   **可能和网页里看到的差几个字符**（非法字符换成 `_`、结尾的空格和点被削掉）。
   → 导出结果里那句提示写「导出了 30 张」，别写「名字和网页里一模一样」。
7. **导出是同步的**，勾 30 张大约要等十几秒到几十秒，期间页面不能刷新。
   → 前端必须有走秒提示 + 「别刷新」。
8. **标签不查重（跨照片）**。同一个 `A1-1` 可以标在两张照片上 —— 只做了**同一次提交内**
   的查重。跨照片查重要多一次全表扫描，而价值不大（用户是照着实拍图填的）。
   → 真撞上重名**导出也不会丢文件**：后一个自动变 `A1-1 (2).png`，并在结果里数出来
   （见 4.6）。

  - 没标定的图**也让导出成功**（不抛异常），且那个文件里没有品红的线
  - 空列表 → 400；勾的 id 一个都找不到 → 400
  - 不存在的 id 混在中间 → 跳过、记进 `failed`，其余照常导出
  - ⚠️ **测试里必须 monkeypatch 掉 `os.startfile`** ——
    不然跑一次 pytest 会满屏弹文件夹窗口（而且会卡住等它关）
- `_safe_segment` 单测（**这一组最要紧**）：
  - `..\..\Windows` → 不含 `..`、不含反斜杠
  - `D:\某处` → 不含冒号
  - `CON` / `nul` / `COM1` → 被加前缀
  - `a<b>c:d"e|f?g*h` → 非法字符全被换掉
  - 结尾是空格或点 → 被去掉
  - 超长 → 截到 60
  - 空串 / 全非法 → `未命名`
  - **端到端**：拿上面每一个恶意名真跑一次导出，断言最终路径仍在 `导出/` 底下
- 重名：两张算出来同名 → 第二个是 `xxx (2).png`，且结果里 `renamed` = 1
- `exporter.export_image()` 单测：标定过的比没标定的**多出标注**
  （用像素统计断言"有品红的线"即可，不比对整图）
