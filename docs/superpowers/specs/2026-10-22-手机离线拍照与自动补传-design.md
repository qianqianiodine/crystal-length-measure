# 手机离线拍照与自动补传 — 设计文档

日期：2026-10-22
状态：已与用户确认方向，待评审

## 1. 背景

晶体房的 Wi-Fi 信号很差。用户很喜欢现在「扫码上传」的方式，因为它允许**拍一张晶体就立刻填上它属于哪个孔**。但拍照后要马上把几 MB 的原图传回电脑，网络一差就传不上去。

用户的需求原话：

> 我们晶体房的网络太差了，但我很喜欢扫码上传，因为这样我可以拍一张晶体就填一次它是哪个孔的，你看我能不能拍一张填一张，然后我离开晶体房到有网的地方统一自动上传？

另一个问题：

> 现在上传记录仍然看不到我自己手动的命名。

## 2. 用户确认过的前提

以下都是用户在本次对话里明确回答的，设计必须遵守：

| 问题 | 回答 |
|---|---|
| 晶体房里，手机能打开传照片页面吗？ | **能打开，只是传照片慢/常失败** |
| 离开晶体房到「有网的地方」，还能连到这台电脑吗？ | **能，还是同一个 Wi-Fi/内网，只是信号好了** |
| 手机传图窗口（现在 2 小时）改多长？ | **保持 2 小时** |
| 照片传回电脑后还要不要手动「确认导入」？ | **不要，传完直接入库** |
| 用什么手机？ | **iPhone / iPad** |
| 一次最多拍多少张？ | **最多 96 张，一般 30～40 张** |

## 3. 目标

1. 手机页拍照后，**照片和标注先存在手机本地**，断网不丢。
2. 回到有网环境，页面**自动一张张补传**，不需要用户逐张点。
3. 传上去的照片**直接进图库**（用户选择），名字、孔位标签、文件夹随上传一起写入。
4. 网络差导致的「电脑收到了、手机没收到回执」不会产生重复照片。
5. 「传送记录」显示**最终入库的名字**（修掉用户报的问题）。
6. 页面明确显示待上传张数和占用大小；存不下时当场报错，不静默丢照片。

## 4. 非目标（明确不做）

- **不做 Service Worker / PWA / HTTPS**。手机访问的是 `http://局域网IP:端口`，不是安全上下文，Service Worker 注册不了；要做得给电脑配证书、再在 iPhone 上装信任证书，代价远超收益。用户已确认「晶体房里页面能打开」，所以不需要「没网也能重新加载页面」。
- **不做锁屏/后台自动上传**。iOS 会在锁屏后暂停网页 JS；页面必须在前台才会传。这一点写进界面提示。
- **不压缩照片**。存的是原图，测量精度不受影响。
- **不改电脑端的上传流程**。电脑端一次传多张仍然进「待确认导入」列表，手机新流程不碰它。
- **不做自动确认入库**——用户明确选择「传完直接入库」，即手机上传走 direct，不经过待确认列表。

## 5. 方案总览

```
iPhone Safari
┌────────────────────────────────────────────┐
│ 页面（/m/<令牌>，加载一次后一直可用）        │
│                                            │
│ 拍照 → File ──► IndexedDB 队列（原图 Blob）  │
│                    │                       │
│                    ├─ 名字 / 编号+行列为孔   │
│                    ├─ 文件夹                │
│                    └─ 状态（等待/传/失败）   │
│                    │                       │
│        每 15 秒 / 回到前台 / online 事件     │
│                    ▼                       │
│   POST /m/<令牌>/upload?mode=direct&folder=N│
│   表单：files + name + tag + uid            │
└────────────────────┬───────────────────────┘
                     │ 同一个 Wi-Fi
                     ▼
              电脑（FastAPI）
         uid 去重 → 直接入库 images 表
```

关键点：**照片在本地存住**，上传只是「把它送走」；送不走就一直留着。

## 6. 手机页设计

### 6.1 页面结构（从上到下）

1. 标题「传照片到电脑」+ 一句新说明：
   「选好照片先存在手机里，填好编号和孔位；回到有网的地方，这个页面会自动一张张传到电脑。」
2. 「拍照 / 选照片」按钮（现有 file input，支持多选）。
3. **新增「待上传（N 张，约 X MB）」区块**：
   - 每行：缩略图 + 名字输入框 + ✕；第二行是「编号」输入框 + 行/列/孔三个下拉；第三行是状态。
   - 区块底部一个「现在全部传」按钮。
   - N 和 X 由本地队列实时汇总（`sum(blob.size)`）。
4. 「这批照片放到」文件夹下拉（现有，保留）。
5. 「传送记录」区块（现有，保留；状态用「已入库」）。
6. 「待确认导入」区块（现有，保留；手机新流程不再往里加，只有电脑端多张上传留下的行会显示）。

### 6.2 本地队列的数据

IndexedDB：数据库 `jltx_offline`，版本 1，对象仓库 `queue`，主键 `uid`。

每条记录：

```js
{
  uid: "随机唯一串",       // 上传幂等键
  blob: File,              // 原图，不压缩
  filename: "IMG_1234.JPG",
  name: "",                // 发给服务端的名字；空 = 用文件名
  no: "",                  // 「编号」输入框里用户打的字
  tag: "",                 // "B5-1" 或空
  folderId: null,          // 整数或 null
  createdAt: 1729560000000,
  touchedAt: 1729560000000,// 最后一次操作时间，用来判断"停手 30 秒"
  status: "wait",          // wait | sending | error
  error: ""                // 失败原因（中文，直接显示）
}
```

`uid` 生成：`crypto.randomUUID()`；老浏览器回退到
`Date.now().toString(36) + '-' + Math.random().toString(36).slice(2)`。

### 6.3 拍照后的流程

1. `<input type="file">` 的 `change` 事件里，逐个 File：
   - 生成 `uid`，构造队列记录，`await qPut(it)` 写进 IndexedDB。
   - **写成功后**才把它加进内存列表并画出来。写失败（通常是手机空间不够）→ 当场显示
     「手机空间不够，这张没存下来：IMG_1234.JPG」，不添加空行、不静默丢。
2. 新行追加到列表末尾，并 `scrollIntoView`，让用户马上看到。
3. 调用一次 `syncQueue()`（它自己会遵守 30 秒规则，不会刚拍完就传）。

### 6.4 「停手 30 秒」规则

- 每次用户在这一行里打字、改下拉，更新 `touchedAt = Date.now()`（并防抖写回 IndexedDB）。
- 一张照片只有在 `now - touchedAt >= 30000` 时才允许自动上传。
- 「现在全部传」按钮忽略这个限制，强制传所有（包括 error 状态的，用于改完名字重试）。

这样用户拍完慢慢填也不会被抢传；填完停手 30 秒，它自己就走了。

### 6.5 上传

请求：

```
POST /m/<令牌>/upload?mode=direct&folder=<id 或省略>
Content-Type: multipart/form-data
  files = 原图 Blob（一张一个请求）
  name  = 队列里的 name（空则不传）
  tag   = 队列里的 tag（空则不传）
  uid   = 队列里的 uid
```

- 一次只传一张，传完再传下一张（手机上看得见进度，也不占内存）。
- 单张请求 60 秒超时（`AbortController`）；超时当作网络失败，留着下次重试。
- 成功判定：HTTP 2xx 且 `d.ok.length > 0`。
- **HTTP 2xx 但 `ok` 为空、只有 `failed`**（例如名字太长被 `_validate_name` 拒绝：
  `_ingest` 会把它收进 `failed` 而不是抛 4xx）→ 按「单张失败」处理：
  状态 `error`，显示 `failed[0].reason`，保留这一行，继续下一张。
- 成功后的动作：
  1. 从 IndexedDB 删掉这一条；
  2. 从内存队列删掉并重画；
  3. 往「传送记录」加一条：`{name: d.ok[0].name, st: '已入库', cls: 'ok'}`；
  4. 继续下一张。

失败分类：

| 情况 | 处理 | 行上显示 |
|---|---|---|
| fetch 抛错 / 超时 | 状态回到 `wait`，**停止本轮循环**（网络断了，后面的也白试） | 连不上电脑，等有网会自动重试 |
| HTTP 403 | 状态 `wait`，本轮停止，60 秒内不再重试 | 电脑上的「手机传图」关了（每 2 小时要重新开一次） |
| HTTP 400 / 422 | 状态 `error`，**保留**，继续下一张 | 服务端给的中文原因（名字太长、孔位不对等） |
| HTTP 5xx | 状态 `wait`，继续下一张 | 电脑那边出了点问题，等会儿自动重试 |

`error` 状态不自动重试，避免一张坏照片卡死整条队列；用户改完名字点「现在全部传」会重试。

### 6.6 重试时机

- 页面加载、队列读出来之后；
- `window` 的 `online` 事件；
- `document.visibilitychange` 变回可见；
- 每 15 秒一次（仅页面可见时）；
- 用户点「现在全部传」；
- 行里的名字/下拉改动之后（30 秒规则仍生效）。

用 `syncing` 布尔量保证同一时刻只有一轮在跑。

### 6.7 名字与孔位（沿用现有规则）

- 三个下拉 → `tag`，格式 `B5-1`（行 + 列 + 第几个孔），必须匹配服务端的 `_TAG_RE`。
- 「编号」+ `tag` → 名字 `编号-B-5-1`（和现有 `nameWithPlate` 一致）。
- 名字输入框也可以直接打自由名字；它是最终发给服务端的 `name`。
- 行/列没选 → `tag` 为空，名字就只是「编号」本身（如果填了）。
- 编号留空 → 名字为空 → 服务端用原始文件名（`_name_from_file`）。

### 6.8 文件夹

- 打开页面时，文件夹树从 `localStorage['jltx.folders']` **先**读出来（断网也能显示）；
  联机时服务端返回的树会覆盖缓存。
- 新队列行使用当前「这批照片放到」的值。
- 用户改这个下拉时：
  - 更新 `localStorage['jltx.folder']`；
  - 把**所有还没上传成功**的队列行的 `folderId` 一起改掉（和现在「这批放到」的语义一致）；
  - 仍然调用一次服务端的 `/m/<令牌>/imports/folder`（为了电脑端留下的待确认行），失败就忽略。
- 服务端收到一个不存在的 folder id 时按 `None` 处理（现有 `_ingest` 已如此）。

### 6.9 传送记录（含用户报的 bug）

- 新流程：上传成功时直接用**服务端返回的最终名字**（可能带 `(2)` 后缀）记录，所以一定对。
- 旧流程（待确认列表）：
  - 现在只在 `paintPend()` 里同步名字，而改名成功后不会重画整表，所以记录停在手机文件名。
  - 修法：在「名字框改名成功」「编号框改名成功」「孔位下拉改名成功」三处，更新完
    `it.name` 后立刻调用 `syncSentNames()`。
- 记录仍然存 `sessionStorage`（锁屏重载不丢，关标签页清空），不变。

### 6.10 断网时的页面行为

- `loadPend()` 用 try/catch 包住；断网时静默失败，不弹错、不白屏。
- `navigator.onLine === false` 时不发上传请求，直接显示「等有网自动传」。
- 页面本身不做离线缓存；断网时刷新会打不开。照片和标注仍在 IndexedDB 里，
  回到有网的地方重新打开同一页面会继续。

## 7. 服务端设计

### 7.1 数据库

`images` 表新增一列：

```sql
client_uid TEXT        -- 手机那边给这张照片的唯一编号；电脑端上传为 NULL
```

- 新库：写进 `SCHEMA` 的 `CREATE TABLE images`。
- 老库：加进 `MIGRATIONS`，启动时 `ALTER TABLE` 补列。
- 唯一索引（允许多个 NULL）：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_images_uid
ON images(client_uid) WHERE client_uid IS NOT NULL;
```

  在 `init_db()` 里 `_migrate()` 之后执行，保证老库补完列再建索引。

`db.py` 新增：

```python
def get_image_by_uid(conn, uid: str) -> sqlite3.Row | None
```

`create_image(...)` 增加关键字参数 `client_uid: str | None = None` 并写入。

### 7.2 上传接口

`POST /m/{token}/upload` 增加三个可选表单字段：

| 字段 | 类型 | 规则 |
|---|---|---|
| `name` | str | 非空时走 `_validate_name`（≤100 字、禁 `storage.BAD_NAME_CHARS`）；空/不传 → 文件名派生（老行为） |
| `tag` | str | 非空时必须 `_TAG_RE.fullmatch`，否则 400「标签「X」不对，应该是 A1-1 这样的」；服务端存成 `json.dumps([tag])` |
| `uid` | str | 1～64 字符；相同 uid 已存在 → 直接返回已有那张，不再写盘/入库 |

只在 `mode=direct` 时生效。`mode=pending` 保持现有行为（手机新页面不会再用它）。

`_ingest(...)` 增加 `name=None, tag=None, uid=None` 三个可选参数：

- **direct 路径**逐张处理：
  1. 若 `uid` 有值，先 `db.get_image_by_uid()`；命中 → 把已有图像的 summary 放进 `ok`，
     `duplicate=True`，**不读盘、不写盘**。
  2. 否则 `_import_one(..., name=name, tags=tags, client_uid=uid)`。
- `_import_one`：
  - 名字 = `_validate_name(name)`（有 name）或 `_name_from_file(filename)`（无），再 `_unique_name`；
  - `db.create_image(..., tags=tags, client_uid=uid)`。
- **并发兜底**：两个请求同时带同一个 uid 时，第二个 `INSERT` 会撞唯一索引。
  捕获 `sqlite3.IntegrityError` → 把刚写下的那份原图 `storage.trash_file()` 掉 →
  重新按 uid 查已有那张返回。绝不留孤儿文件。
- 返回结构保持不变：`{"ok": [...], "failed": [...], "staged": [...]}`，
  另加一个布尔 `"duplicate": true|false`（稳定形状，测试用）。
  **命中已有 uid（预查或并发兜底）都置 `duplicate=true`**。

### 7.3 API 版本

`app/config.py` 的 `API_VERSION` 21 → **22**，并写日期注释：
手机页存在服务端内存里、接口形状变了，不 +1 的话用户会看到新页面打老接口。

## 8. 数据安全与容量

### 8.1 容量估算

- iPhone Safari 每个网站大约 1GB 量级（苹果未公开保证具体数字，系统空间紧张时可能清理）。
- 原图不压缩，一张通常 3～6MB：
  - 30～40 张 ≈ 100～240MB —— 安全；
  - 96 张 ≈ 300～600MB —— 通常存得下，但建议中途传一次。
- 页面顶部实时显示「待上传 N 张，约 X MB」。
- 写入 IndexedDB 抛 `QuotaExceededError` 时，当场提示哪张没存下，不添加空行。

### 8.2 必须告诉用户的限制（写进页面提示或使用说明）

1. 网页拍的照片**不在 iPhone 相册里**；传上去之前，手机浏览器里是唯一一份。
2. 别清 Safari 数据、别换手机、别重装浏览器。
3. iPhone 锁屏后网页会被暂停；自动上传只在页面打开且在前台时执行。
4. 页面在没网时被系统刷新/关掉会打不开；照片和标签还在，回到有网的地方重新打开即可。
5. 手机队列跟「网址」绑定：电脑 IP 或端口变了，新地址上看不到旧队列。回办公室先传完，别攒到第二天。
6. 2 小时窗口关了以后，手机显示「电脑上的手机传图关了」；回电脑点一次「开启手机传图」，自动接着传。
7. 拍完不填编号的照片，停手 30 秒后也会用手机文件名入库，不会卡住队列。

## 9. 测试设计

### 9.1 Python（服务端）

在 `tests/test_api_imports.py`（或新的 `tests/test_api_mobile_queue.py`）里加：

- 带 `name` 的直接上传 → 入库名字就是给的名字。
- 带 `tag` 的直接上传 → `images.tags` 是 `["B5-1"]`。
- 非法 `tag` → 400，中文提示。
- 同一个 `uid` 传两次 → 只入库一张；第二次 `duplicate=true`；`data/images/originals` 里只多一个文件。
- 同 uid 但第二次 name 不同 → 返回第一次那张的名字，不新建。
- 不带 uid 的老调用 → 行为不变（现有测试已覆盖）。
- `folder` 仍然生效。
- 数据库层：`get_image_by_uid` 能查到；同一 uid 不能插两次。

### 9.2 页面行为检查（`tests/web_behavior_check.mjs`）

需要一个极简的 IndexedDB 假实现（内存 Map + 微任务回调），只支持页面用到的
`open / createObjectStore / transaction / put / delete / getAll`。

- Q1：选一张照片后，先写进本地队列，**不立刻发上传请求**。
- Q2：`touchedAt` 超过 30 秒 + 在线 → 自动上传，请求里带 `name`、`tag`、`uid`、`folder`。
- Q3：上传成功 → 本地队列清空，传送记录显示服务端返回的最终名字、状态「已入库」。
- Q4：fetch 失败 → 队列保留，状态文字包含「等有网」。
- Q5：返回 403 → 状态文字包含「手机传图」和「关了」。
- Q6：返回 `ok` + `duplicate:true` → 本地也删掉，不重复记录。
- Q7：待确认行改名成功后，传送记录里的名字**立刻**跟着变（修好的 bug）。

### 9.3 人工验收（用户做）

1. 有网时扫码打开页面。
2. 开飞行模式/走到信号差的地方，拍 3 张，分别填编号 + 孔位。
3. 确认三行都在「待上传」里，显示张数和 MB。
4. 恢复网络，页面在前台等 ≤ 20 秒，确认三张自动传完、状态「已入库」。
5. 到电脑图库确认三张都在，名字是「编号-行-列-孔」。
6. 关掉页面再重新打开，确认「传送记录」里名字是对的。
